# Сервис генерации

Сервис принимает заказ на генерацию, списывает токены и отдаёт задачу провайдеру. Если провайдер отказал, сервис переходит к следующей ноге модели. Если отказали все — возвращает токены. Каждое движение денег записывается строкой в журнал операций и происходит ровно один раз.

Регистрации, авторизации, UI и настоящего хранилища файлов нет. Результат генерации — строка-ссылка. Пользователь создаётся при первой оплате со `status=paid`.

## Запуск

Нужны Docker и Docker Compose.

```bash
docker compose up --build
```

Команда поднимает PostgreSQL, API в **4 процесса** (`uvicorn --workers 4`) и фейковых провайдеров `alpha` и `beta`. На старте API применяет миграции: `alembic upgrade head`.

Проверка:

```bash
curl http://localhost:18000/health
```

Ожидаемый ответ: `{"ok":true}`.

| Компонент | URL с хоста |
| --- | --- |
| API | http://localhost:18000 |
| Провайдер `alpha` | http://localhost:18001 |
| Провайдер `beta` | http://localhost:18002 |
| PostgreSQL | localhost:15432 |

Порты на хосте сдвинуты с 8000, чтобы не пересекаться с другими сервисами. Внутри сети compose API слушает порт 8000.

Общий секрет подписи вебхуков: `test-secret`. Заголовок `X-Signature` — HMAC-SHA256 сырого тела, hex. Таймаут ожидания провайдера: `PROVIDER_TIMEOUT=60` секунд.

Остановка: `docker compose down`. Удалить данные БД: `docker compose down -v`.

## Тесты

Тесты ходят в живой стек из compose, не в моки. Обязательные сценарии:

1. 20 одновременных одинаковых вебхуков оплаты дают одно начисление.
2. 10 одновременных `failed` по одной задаче на последней ноге дают один возврат.
3. Отказ первой ноги: задача завершается на второй, в истории две попытки.
4. Поздний `completed` после срабатывания сторожа обрабатывается по правилу 6 (ниже).

Тест 4 ждёт сторожа (`PROVIDER_TIMEOUT` = 60 с). Полный прогон занимает около двух минут.

Из контейнера API:

```bash
docker compose up --build -d
docker compose exec -e API_URL=http://127.0.0.1:8000 \
  -e ALPHA_URL=http://alpha:8000 \
  -e BETA_URL=http://beta:8000 \
  api pytest -q
```

С хоста (после `pip install -r requirements.txt`):

```bash
pytest -q
```

По умолчанию тесты с хоста обращаются к `localhost:18000`, `18001`, `18002`.

## Миграции

Схема создаётся только миграциями Alembic.

Применить текущие (так делает контейнер API):

```bash
alembic upgrade head
```

Добавить следующую:

```bash
alembic revision -m "описание изменения"
```

Затем отредактировать файл в `alembic/versions/` и снова выполнить `alembic upgrade head`.

Для запуска Alembic с хоста укажите `DATABASE_URL=postgresql+asyncpg://gen:gen@localhost:15432/gen`. Alembic подменяет драйвер на `psycopg2`.

Каталог моделей заносится первой миграцией:

| Модель | Цена, токенов | Ноги по приоритету |
| --- | --- | --- |
| `image-fast` | 2 | `alpha`, до 4 референсов → `beta`, до 10 |
| `video-long` | 25 | `beta`, до 2 → `alpha`, до 1, `skip_on_moderation` |

## API

- `POST /generate` `{user_id, model_slug, prompt, ref_images}` — списывает цену, создаёт задачу, отправляет на первую подходящую ногу, отвечает `task_id`. Не хватает токенов — 402. У пользователя уже 3 активные задачи — 429. Ни одна нога не принимает столько референсов — 400 **до** списания.
- `POST /webhooks/providers/{name}` — результат от провайдера (`alpha` или `beta`).
- `POST /webhooks/payments` — `{payment_id, user_id, tokens, status}` с той же подписью. Кредит только при `status=paid`. Одна оплата может прийти несколько раз и одновременно.
- `GET /tasks/{id}` — статус, текущая нога и история попыток: провайдер, тип ошибки, время.
- `GET /users/{id}/balance` — баланс и последние строки журнала. Баланс пользователя всегда равен сумме его журнала.

Провайдер принимает `POST /tasks` и сразу отвечает `202 {"external_id": "..."}`. Через 2–20 секунд присылает вебхук: `completed` со ссылкой или `failed` с типом `technical`, `moderation` или `payload`.

Поведение провайдера для тестов задаётся `PUT /admin/settings` на `alpha`/`beta`: доля отказов и тип ошибки; синхронный 503 или таймаут на `POST /tasks`; двойной вебхук, в том числе одновременный; вебхук не приходит; `completed` после `PROVIDER_TIMEOUT`.

## Ровно один раз: начисление и возврат

Деньги меняются только вставкой строки в `ledger_entries`. Поля баланса в памяти процесса нет.

- Начисление оплаты защищено уникальным индексом по `payment_id`: повторные и одновременные вебхуки дают одну строку `payment`.
- Списание — одна строка `charge` на задачу.
- Возврат — одна строка `refund` на задачу, сколько бы вебхуков `failed` ни пришло.
- `users.balance` пересчитывается триггером как `SUM(amount)` журнала. Операций без строки в журнале нет. Ограничение `balance >= 0` не даёт уйти в минус при гонке списаний.

Сторож и синхронные ошибки (5xx, таймаут `POST /tasks`) ведут туда же, куда отказ в вебхуке: к следующей ноге или к единственному возврату.

Состояние хранится в PostgreSQL. Четыре воркера не расходятся. Сторож запущен в каждом процессе; просроченные попытки он берёт через `SELECT ... FOR UPDATE SKIP LOCKED`, поэтому failover не задваивается.

## Падение процесса посреди обработки вебхука

1. Подпись проверяется по сырому телу до любой записи в БД. Неверная подпись — 401, журнал не трогается.
2. Смена статуса задачи и строка журнала выполняются в одной транзакции.
3. Если процесс упал до `COMMIT`, транзакция откатывается. Повтор вебхука обрабатывается заново.
4. Если процесс упал после `COMMIT`, но до ответа HTTP, повтор упирается в уникальный индекс или в уже терминальный статус задачи и отвечает 200 без второго начисления или возврата.

## Правило 6: поздний `completed`

Если провайдер молчит дольше `PROVIDER_TIMEOUT`, сторож считает попытку неудачной и ведёт задачу дальше по общим правилам (следующая нога или единственный возврат).

Если после этого приходит `completed`, задача **не** получает и результат, и возврат. Принятое решение: терминальное состояние неизменно. Побеждает то, что записалось первым. Сторож уже перевёл задачу в `failed` и записал возврат — поздний `completed` подтверждается HTTP 200 и игнорируется: `result_url` не заполняется, возврат не отменяется.

Обратный вариант (принять файл и забрать токены обратно) дал бы либо бесплатную генерацию, либо повторное списание после возврата. Поздний успех провайдера на финансовый журнал не влияет.
