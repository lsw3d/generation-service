# Сервис генерации

Принимает заказ, списывает токены, отправляет задачу провайдеру и перебирает «ноги» модели. Деньги двигаются только строками журнала, каждая — не больше одного раза, даже если вебхук пришёл двадцать раз в четыре воркера.

## Запуск

Нужны Docker и Docker Compose.

```bash
docker compose up --build
```

Поднимаются PostgreSQL, API (`uvicorn --workers 4`) и фейковые провайдеры `alpha` (порт 8001) и `beta` (8002). На старте API применяет миграции: `alembic upgrade head`.

Проверка: `GET http://localhost:18000/health`. На хосте порты `18000` (API), `18001` (alpha), `18002` (beta), чтобы не пересекаться с занятыми 8000–8002.

## Тесты

Тесты ходят в живой стек из compose.

```bash
docker compose up --build -d
pip install -r requirements.txt
pytest -q
```

Переменные по умолчанию: API `http://localhost:18000`, секрет подписи `test-secret`. `PROVIDER_TIMEOUT` в compose равен 60 секундам — тест позднего `completed` ждёт сторожа.

## Миграции

Схема живёт в Alembic, не в `create_all`.

- Применить текущие: `alembic upgrade head` (так делает контейнер API).
- Добавить следующую:

```bash
alembic revision -m "add_something"
# правите alembic/versions/<revision>_add_something.py
alembic upgrade head
```

`DATABASE_URL` для миграций тот же, что у сервиса (`postgresql+asyncpg://...`). Alembic сам подменяет драйвер на `psycopg2`.

## Ровно один раз: начисление и возврат

Источник истины — таблица `ledger_entries`, а не поле в памяти и не «сначала обновим баланс».

- Начисление оплаты: уникальный индекс по `payment_id`. Двадцать одинаковых вебхуков дают одну строку `payment`.
- Списание: одна строка `charge` на задачу (уникальный индекс по `task_id`).
- Возврат: одна строка `refund` на задачу. Сколько бы `failed` ни пришло на последнюю ногу, вставится один возврат.
- `users.balance` пересчитывается триггером как `SUM(amount)` журнала. Приложения не пишут баланс напрямую. Ограничение `balance >= 0` закрывает гонку двух списаний.

Смена статуса задачи — `UPDATE ... WHERE status = 'running'`. Первый коммит делает задачу `completed` или `failed`; остальные вебхуки отвечают 200 и ничего не меняют.

## Падение процесса посреди вебхука

1. Подпись проверяется по сырому телу до записи в БД.
2. Статус задачи и строка журнала меняются в одной транзакции. Нет окна «деньги уже списали/вернули, а статус ещё нет».
3. Если процесс умер до `COMMIT`, транзакция откатывается. Провайдер (или платёжка) присылает вебхук снова — уникальный индекс или уже терминальный статус превращают повтор в no-op, ответ 200.
4. Если процесс умер после `COMMIT`, но до ответа HTTP, повтор упирается в тот же индекс / CAS.

Состояние попыток и баланса в Postgres, поэтому четыре воркера не расходятся. Сторож есть в каждом процессе, но просроченные попытки берёт через `SELECT ... FOR UPDATE SKIP LOCKED`: одну строку обрабатывает один воркер.

## Правило 6: поздний `completed`

Терминальное состояние неизменно. Если сторож уже закрыл попытку как `timed_out`, перевёл задачу в `failed` и записал возврат, поздний `completed` подтверждается и игнорируется: `result_url` не пишется, возврат не откатывается.

Иначе пользователь получил бы и файл, и токены (бесплатная генерация) либо повторное списание после возврата. Поздний успех провайдера — потерянный артефакт, не финансовая операция.

## API

- `POST /generate` `{user_id, model_slug, prompt, ref_images}` → `{task_id}`. 402 без токенов, 429 если уже 3 активные задачи, 400 если ни одна нога не принимает столько референсов (до списания).
- `POST /webhooks/providers/{alpha|beta}` — результат провайдера, заголовок `X-Signature` = HMAC-SHA256 сырого тела.
- `POST /webhooks/payments` `{payment_id, user_id, tokens, status}` — та же подпись; кредит только при `status=paid`. Пользователь создаётся при первой оплате.
- `GET /tasks/{id}` — статус, текущая нога, история попыток.
- `GET /users/{id}/balance` — баланс и последние строки журнала.

Фейковые провайдеры: `PUT /admin/settings` задаёт долю отказов, синхронный 503/таймаут, двойной вебхук, молчание и поздний `completed`.
